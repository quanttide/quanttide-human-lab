# p02 绩效观测工具 — 实验方案

## 实验目的

验证「意义从事后观测中浮现」：不做事前清单，只看实际产出 + 周期回看，创始人能否读出自己工作的主线与意义。

## 背景

意图仓绩效模块（`data/intention/performance/founder.md`）记录了绩效制度的演化：2025 年判例是事前清单 + 考核（清单已收入制度史 `data/history/performance/founder.md`）；2026 年进化为观测工具——创始人每天做一堆事，事前说不出每件事的意义，绩效改为如实记录每天的工作，意义从事后的观测里逐渐浮现。观测让工作先被看见，看见是考核的前提。

本实验验证这个进化方向是否真的成立：观测能不能替代事前断言，把意义找回来。

观测的数据源是实际产出，不是自我报告。创始人的产出目前主要集中在 GitHub——个人账号与 quanttide 组织下的提交、PR、发布、新建仓库，产出留痕天然存在，观测不需要任何额外的记录流程。

## 实验假设

1. 每日事务如实记录后，按周期回看能识别出重复出现的工作主题，主线可以从事后数据里读出来，不需要事前定义
2. 「说不清意义」的事务占比是可测量的，不是一个模糊感受——观测能把意义缺位定位到具体条目
3. 事后读出的意义可以转化为下个周期的事前判断：观测 → 意义 → 新的清单，闭环成立

## 实验设计

### 阶段 1：产出基线（第 1 周）

不新建记录流程，数据源直接用 GitHub 产出：取最近一周内个人账号与 quanttide 组织的**产出物**——写作（日记、稿件）、发布（版本、Release）、新建仓库、体系动作（术语定版），逐件列成产出物清单，每件标注：

| 字段 | 说明 |
|------|------|
| 日期 | 产出物当周出现的日期 |
| 类型 | 写作 / 产品 / 组织 / 体系 |
| 结果 | 已发布 / 已落盘 / 已铺底 |
| 意义 | 事前能否一句话说清为什么做（能/不能 + 原话） |

> 提交普查不作观测单位：git 事件是产出的传播半径（指针同步、日记扇出、术语批量改写），只作背景口径附注。首轮曾以提交为单位交付，被判设计偏差，反思见 `2026-10-30-设计偏差反思.md`。

### 阶段 2：观测回看（第 2 周）

对一周的产出物清单做三件事：

1. 按类型清点，看哪条线的产出物体量最大
2. 标出每件产出物的传播半径（一次产出被放大成多少提交）——传播不算独立工作
3. 找出意义空白：哪些产出物事前说不出为什么做（产出物层面，不是提交层面）

### 阶段 3：推测—校准—沉淀（每周）

1. AI 拉产出物，做语义解读 + 业务目的推测
2. 创始人逐条一句话校准（对 / 错 / 改写）
3. 校准句入档案仓 `data/profile/quanttide-founder/performance/`，按业务线沉淀（线是文件、天是行）

> 约束：只读出「这条线是什么」，不做「这个为什么值得」的审计；观测报告不带评价词；推测若无业务上下文必错（qtcloud 首轮弃置/搁置两猜皆错，真实原因是功能迁往专用平台），校准句只能是创始人的话。

### 阶段 4：闭环验证（下一季度）

把读出的意义写成下季度的事前清单，交 HR 考核，季度末对账：观测数据支撑的事前断言，比拍脑袋的断言更准吗？

## 评价标准

| 指标 | 合格线 |
|------|--------|
| 从一周产出物归纳出的主线数量 | ≤ 3 条，且每条能用数据指回具体产出物 |
| 意义空白的产出物 | 至少指出 1 件 |
| 阶段 3 的意义陈述 | 被下季度清单采纳，且季度末可对账 |

## 原型实现

首轮不写代码：阶段 1–3 手工完成，先验证观测本身有没有价值。只有手工回看被证明有效、且每周回看成本过高时，才做「GitHub 产出 → 产出物 → 聚类统计」的脚本或观测面板。

## 实验记录

每次回看后在本目录追加记录：

- 产出物清单与传播半径
- 读出的主线与依据
- 意义空白的产出物
- 对实验设计的调整（设计偏差一律先写带日期的反思归档，再改设计）

> 注意：实验记录可能涉及私有仓库的产出，入仓前必须脱敏（规则见根仓 AGENTS.md），只留方法、统计和结论，不留带业务细节的原始条目。

## 下一步

观测流程稳定后，把「GitHub 产出 → 产出物 → 聚类」做成脚本（GitHub API / gh CLI），接入人事云（qtcloud-human）成为常驻的观测能力。
